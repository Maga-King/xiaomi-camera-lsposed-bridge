# 最后版本、证据与处理边界

## 版本确认

本地两代工程中，早期 `xiaomi_camera_lsposed` 的 `local.mio.micambridge`、0.5.44 并不是后续徕卡 M3 研究的最新工程。

后续工程是 `os4_camera_lsp`。本次找到的最终产物为 `camera-legend-native-r17.apk`，文件生成时间 2026-09-09 14:27，APK 声明 versionCode 202、`0.4.92-live-photo-r17`。当前 Java 工程的 Gradle 版本号仍为 187/0.4.77，二者差异来自增量 Smali 发布方式。

仓库保存最终部署 APK 自有包的 366 个 Smali 文件，以及当时的开发源码。不发布整套第三方反编译应用或原始设备日志。

## 真实处理路径

1. 在小米自己的效果/水印保存之前接入同一张照片；M3/M9 主摄分支取欧加 Photo APS 的干净 JPEG，避免把水印区域再次送进算法。
2. `LegendaryNativeCaptureBridge` 校验拍摄模式和保存条件，将数据交给专用 Provider；失败时保留原 JPEG，不把失败图片标成成功算法结果。
3. `LegendaryProcessingProvider` 按 Binder 调用 UID 校验自身、root 或 `com.android.camera` 调用方；借助文件描述符传递工作数据。
4. 解码 JPEG 像素，经 BT.601 full-range NV12 转换后交给隔离 native worker。worker 有超时控制，避免无限阻塞保存链。
5. M3 对应 mode=2：加载 `libmialgo_monopan.so`，调用 Monopan 的初始化、处理、释放入口，并按原 wrapper 的处理顺序中和色度。不是把普通照片直接灰度化当作 M3。
6. M9 对应 mode=1：QNN high/low styletrans、colorfix 与 `leica_m9s2_param.bin`，需匹配的 HTP/DSP 和 runtime。原始 RAW 附件仅在相应 M9 分支保留，不与 M3 混用。
7. 转回 RGB、JPEG 编码，再接同一张照片的 EXIF、方向、水印和容器保存。不得拿上一张的元数据或图库内容来充数。

worker 的图形依赖采用私有装载思路，历史上专门处理过 `libgsl.so` / OpenCL 与美颜 namespace shim 的冲突；不能为了本地模型直接替换全系统 GPU/HAL 库。

## 本地执行证据（脱敏摘要）

2026-09-09 的归档运行记录多次出现 mode=2 native provider 完成和 `committed pre-Xiaomi-effect`。一轮阶段耗时为：准备 3 ms、JPEG 解码 449 ms、RGB 转 NV12 并写入 170 ms、worker 403 ms、读取并转回 RGB 212 ms、JPEG 编码 371 ms，总计 1608 ms。随后还有约 1.6 秒的完成记录。

这些证据支持“在当时设备上，M3 本地算法实际执行并产出照片”，不是只写了状态字段。但该日志跨版本累积，不能据此推断 r17 每个新功能都经过完整回归，也不能证明任意新相机版本、任意 SoC 均兼容。
